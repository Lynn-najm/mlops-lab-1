Question 1:
Everything written to /mlflow-data lives only in that container's writable layer, not in the image. docker stop just halts the process — the layer is still sitting on disk — but docker rm deletes that layer permanently. We proved this with marker.txt: after stop+rm and starting a fresh container from the same image, ls /mlflow-data shows no marker.txt at all, and mlflow.db is a brand-new empty file the server just recreated. The new container starts with an empty writable layer stacked on the same unchanged image — none of the previous container's data carries over. Without a volume, every docker rm would delete mlflow's whole database and all registered models.

Question 2:
A bind mount would technically persist the data too, but it's the wrong tool here. mlflow's database and artifacts are runtime state generated by the container, not files we edit by hand — the way source code is for a bind mount. A named volume is fully managed by Docker (created automatically, storage location abstracted away), which makes it portable across machines/OSes and avoids host-file-permission mismatches from the container often writing as root. It also keeps binary runtime data out of the git repo entirely. A bind mount would work, but you'd be exposing internal container state as loose files in your project tree for no benefit, plus real permission friction.

Question 3:
In Lab 3, mlflow ran as a process on the host, outside Docker — from inside the container, "the host" has no name Docker knows about by default, so host.docker.internal exists specifically to let a container reach back out to its host machine. In this lab, mlflow is itself a container, and Compose puts every service in the docker-compose.yml on the same private network, running an embedded DNS server that resolves each service name (mlflow, inference, frontend) to whichever container is running that service. http://mlflow:5000 works because mlflow is now a sibling container on that Compose network, not the host. No code change is needed since serve.py already reads MLFLOW_TRACKING_URI from the environment — only the value passed to it at container-run time changes.

Question 4:
http://inference:8000 only resolves inside a Compose-managed network, where Compose's embedded DNS registers "inference" as the sibling container's hostname. If that were hardcoded and you ran the frontend image standalone with `docker run` (outside Compose, no sibling "inference" container), that hostname wouldn't exist and the request would fail with a DNS error. Reading INFERENCE_URL from an environment variable keeps the same image reusable across contexts — inside this Compose stack, standalone against a locally running API, or pointed at a different host entirely — just by changing one env var at run time, no rebuild needed. Same decoupling principle as MLFLOW_TRACKING_URI in serve.py.
